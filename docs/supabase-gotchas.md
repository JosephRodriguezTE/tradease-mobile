# Supabase Operational Gotchas

Hard-won operational lessons about this specific Supabase project (`linqsojbszglbgpoxgtv`) that aren't visible from reading the schema or the code — the kind of thing that gets rediscovered the expensive way if it isn't written down.

## Default privileges silently grant anon/authenticated on every new function, view, or table

This project has a schema-level default-privilege rule that grants `anon` and `authenticated` broad access automatically at creation time — `EXECUTE` on new functions, full `INSERT`/`UPDATE`/`DELETE`/`TRUNCATE` on new tables and views — and `REVOKE ALL ... FROM PUBLIC` does **not** undo it, because `PUBLIC` and the named roles `anon`/`authenticated` are separate grantees; revoking from one says nothing about the other. Hit five times in one engagement before this got written down: `contractors_nearby()` and other `SECURITY DEFINER` functions came back with anon `EXECUTE` after every `DROP FUNCTION` + `CREATE FUNCTION`; the `contractors_public` view came back with anon/authenticated write grants after a `DROP VIEW` + `CREATE VIEW`; and the brand-new `trades`/`contractor_trades` tables got the same treatment on their very first `CREATE TABLE`, despite an explicit `REVOKE ALL FROM PUBLIC` in the same migration. The fix is always explicit and always the same: after creating or recreating any function, view, or table, run `REVOKE <verbs> ON <object> FROM anon, authenticated` for whatever shouldn't be public, then confirm with `information_schema.routine_privileges` (functions) or `information_schema.role_table_grants` (tables/views) — never assume a bare `REVOKE ALL FROM PUBLIC` was enough.
